# 목표

`chanpark-harness` 플러그인의 **Plans.md 기반 태스크 관리 체계를 재설계**하고, 그 설계 결정·근거·마이그레이션 경로를 담은 문서와 실제 구현을 만들어줘.

기준은 **Linear의 이슈 위생 모델**과 **Basecamp Shape Up의 "Bets, Not Backlogs"** 두 가지다.
"정리가 좀 더 잘 되는 수준"이 아니라, **이 두 체계와 나란히 놓고 백로그 팽창 방지력을 비교했을 때 밀리지 않는 수준**이 목표다.

제약:
- 대상 저장소는 `/data/chanp5660/chanpark-harness` (플러그인 자기 자신)
- **순수 `git` 체크아웃만으로 동작해야 한다.** Node/Go 빌드 단계 추가 금지. 셸 + awk + jq만 사용
- `bin/harness-*`는 업스트림 벤더링 바이너리이고 이 저장소에 Go 소스가 없다. 바이너리 동작을 바꿔야 하면 셸 핸들러로 인수하는 기존 패턴(`scripts/hook-handlers/plans-watcher.sh`)을 따를 것
- 사용자 노출 콘텐츠(`agents/`, `skills/`, `output-styles/`, `templates/`)는 **영어만**. 설계 문서는 한국어 가능

---

## 해결해야 할 실패 (실측된 것)

1. **백로그 팽창** — 항목을 추가하는 경로(`harness-plan`)는 있는데 **폐기·중복정리 경로가 없다.** 마커 4종(`cc:todo`/`cc:wip`/`cc:done`/`cc:blocked`) 어디에도 "안 하기로 했다"를 기록할 자리가 없어서, 한 번 들어온 항목은 완료될 때까지 영원히 남는다. `maintenance` 스킬은 `cc:done` 아카이빙만 하며 `cc:todo` 정리는 다루지 않는다.
2. **미읽힘** — 활성 작업과 언젠가 할 일이 한 파일에 섞여 있어 파일이 길어지고, 사용자가 열지 않게 된다. 열지 않으니 정리도 안 되고, 정리가 안 되니 더 길어지는 되먹임이 있다.

## 기준점 상세 (리서치로 확보된 사실 — 설계에 반드시 반영)

### 기준점 A — Linear (상용 이슈 트래커)

- 상태를 **5개로 고정**한다: `Backlog` / `Todo` / `In Progress` / `Done` / **`Canceled`**. 커스텀 상태 남발을 의도적으로 막는다. → **현행 harness에는 `Canceled`에 해당하는 상태가 아예 없다.**
- 우선순위도 5단계 고정: Urgent / High / Medium / Low / No Priority
- **auto-close**: 일정 기간 업데이트되지 않은 이슈를 자동으로 `Canceled` 처리한다. 사람이 백로그를 손으로 훑는 일을 없애기 위한 기능이다.
- **auto-archive**: 완료·취소된 이슈를 자동 아카이브해 활성 뷰에서 치운다.
- Linear Method의 명시적 원칙: **"Keep a manageable backlog"**
- Backlog와 활성 보드가 **분리된 뷰**다. 한 화면에 같이 놓지 않는다.

### 기준점 B — Shape Up (Basecamp 방법론)

- **백로그를 아예 유지하지 않는다.** 이유가 명시적이다: *"Backlogs grow forever — items get added faster than they're completed, creating a depressing inventory of broken promises."*
- 대신 **betting table**: 6주 사이클마다 pitch 중에서 무엇을 할지 건다. 후보는 **지난 6주간의 pitch + 누군가 의도적으로 되살린(revive) pitch**뿐이다. 되살려지지 않은 것은 자연 소멸한다.
- 6주 고정 타임박스 + cool-down 기간
- 핵심 통찰: **"기억하지 않는 것"과 "중앙 백로그를 유지하는 것" 사이에 제3의 선택지가 있다** — 각자 추적하되 중앙 목록에는 올리지 않는다.

### 대조군 C — Task Master (경쟁 에이전트 하네스)

- `tasks.json`이 단일 SoT이고, **사람이 읽는 태스크별 markdown 파일을 거기서 생성**한다. 기계용 SoT와 사람용 뷰가 분리돼 있다.
- 태스크 필드: `id` / `title` / `description` / `status` / `dependencies` / `priority` / `details` / `testStrategy` / `subtasks`
- 상태 변경이 **파일 직접 편집이 아니라 명령**(`set-status`)이고, 순환 의존성 탐지와 타입 검증이 붙어 있다.
- → 현행 harness는 사람이 Plans.md 표를 손으로 편집한다. 이 차이의 득실을 반드시 따져라.

### 대조군 D — GitHub Spec Kit (90k+ stars)

- `constitution.md`에 **불변 원칙**을 두고, Specify → Plan → Tasks → Implement 4단계 체크포인트로 진행한다.

> 위 4개는 모두 공개 자료가 있다. **직접 조사해서 사실을 확인하고 최신 내용을 반영해라.** 위 요약만 믿지 마라.

## 먼저 계측할 것 (추정 금지)

설계 전에 현행 실태를 숫자로 확보해라. 추정치를 근거로 쓰면 그 설계는 폐기한다.

- `git log`로 Plans.md의 **항목 생애주기**를 계측: `cc:todo`로 들어와서 `cc:done`까지 걸린 시간의 분포, 그리고 **끝내 done에 도달하지 못한 항목의 비율과 생존 기간**
- 이 저장소와 아카이브 파일(`Plans-archive-*.md`)에서 **중복·유사 항목**이 실제로 몇 건이었는지
- Plans.md 줄 수의 시간에 따른 변화 추이

## 병렬로 진행할 것 (서브에이전트 팬아웃)

아래는 서로 독립적이다. 각각 별도 서브에이전트에 배분해서 동시에 진행해.

- **A. Linear 조사** — 상태 모델, auto-close/auto-archive의 실제 임계값과 설정 단위, backlog/active 뷰 분리 방식
- **B. Shape Up 조사** — betting table 절차, pitch 소멸 메커니즘, cool-down의 역할. 6주 사이클을 1인 개발에 축척했을 때 무엇이 남고 무엇이 무너지는지
- **C. 경쟁 하네스 조사** — Task Master / BMAD-METHOD / GitHub Spec Kit / OpenSpec / Kiro가 태스크 상태와 폐기를 어떻게 다루는지. **특히 "안 하기로 한 항목"을 각각 어디에 어떻게 기록하는지**
- **D. 현행 실태 계측** — 위 "먼저 계측할 것" 전부
- **E. 영향 범위 매핑** — 마커 문법을 건드렸을 때 깨지는 곳 전수 조사: `scripts/lib/plans-markers.awk`, `hud/statusline.sh`, `scripts/hook-handlers/plans-watcher.sh`, `scripts/hook-handlers/wip-guard.sh`, `scripts/progress-snapshot.sh`, `scripts/ci/check-regression-guard.sh`, 벤더링 바이너리의 카운터 경로, `skills/harness-*`

## 순차로 진행할 것 (쪼개지 마)

**설계안 자체 — 마커 체계 / 파일 분리 구조 / 스킬 변경 / 마이그레이션 절차 — 는 한 에이전트가 처음부터 끝까지 맡아라.**

이유: 이 넷은 전부 **같은 상태를 쓰기한다.** 마커 집합을 바꾸면 파일 분리 규칙이 따라 바뀌고, 파일이 갈리면 어느 스킬이 어느 파일을 쓰는지가 바뀌며, 그 전부가 마이그레이션 절차의 입력이다. 서로를 호출하지 않는다고 독립인 게 아니다.

여기를 병렬로 쪼개면 각 조각은 그럴싸한데 **이음매에서 반드시 터진다** — 새 마커를 제안한 조각과 awk 카운터를 고친 조각이 서로 다른 문법을 가정하는 식으로. 실제로 이 저장소는 v1.3.6에서 바이너리 카운터와 HUD 카운터가 같은 파일을 다르게 세는 사고를 이미 겪었다.

구현도 마찬가지로 순차다. 마커를 읽는 모든 소비자(awk / HUD / 훅 / 스냅샷 / 회귀가드)를 **한 번에** 일관되게 고쳐라.

## 설계안이 반드시 답해야 하는 질문

- 폐기 상태를 새 마커로 도입할 것인가, 아니면 파일 이동으로 표현할 것인가. **선택하지 않은 쪽을 왜 버렸는지 적어라.**
- 백로그를 별도 파일로 분리할 것인가, Shape Up처럼 **아예 유지하지 않을 것인가.** 1인 개발 + AI 에이전트라는 조건에서 각각 무엇이 무너지는지 따져라.
- 자동 만료를 넣는다면 임계값은 며칠인가. **그 숫자의 근거는 위 D 계측 결과여야 한다.**
- 새 아이디어 투입 시 중복 판정을 누가 하는가 — 사람인가, 스킬인가, 훅인가. 판정에 실패했을 때 어느 방향으로 실패하는가.
- 활성 파일 길이 상한을 강제할 것인가. 강제한다면 넘쳤을 때 무슨 일이 일어나는가.

## 검증

만드는 에이전트와 **별개의** 검증 에이전트를 둬라. **자기가 만든 설계를 자기가 채점하지 마라.**

검증자는 가혹한 비평가여야 하고, **Linear와 Shape Up의 공개 자료를 직접 조사해서** 제안된 설계와 나란히 놓고 블라인드로 비교 판정해라. 특히 이 질문에 답해라:
**"이 설계를 6개월 돌렸을 때 백로그가 팽창하는 경로가 남아 있는가?"** 남아 있다면 그 경로를 구체적으로 지목해라.

체크리스트 — 전 항목 Yes여야 통과:

- [ ] 폐기 경로가 상태 수준에서 정의되어 있고(Linear의 `Canceled`에 대응), 기존 4마커와 충돌하지 않는가
- [ ] 활성 작업과 백로그가 물리적으로 분리(별도 파일 또는 별도 섹션)되어 있고, 어느 쪽을 기본으로 열지가 정해져 있는가
- [ ] 자동 만료·강등 규칙이 **구체적 일수**와 함께 명시되어 있고, 그 숫자가 실측 데이터에 근거하는가
- [ ] 새 항목 투입 시 중복 판정 절차가 "무엇과 무엇을 비교해서 어떻게 판단하는가" 수준까지 실행 가능하게 적혀 있는가
- [ ] 활성 파일이 한 화면(80줄 이내)에 들어가도록 강제하는 메커니즘이 있고, 초과 시 동작이 정의되어 있는가
- [ ] 기존 `cc:todo`/`cc:wip`/`cc:done`/`cc:blocked` Plans.md를 **깨뜨리지 않고** 전환하는 마이그레이션 절차가 단계별로 있고, 되돌리는 방법도 있는가
- [ ] 각 변경이 건드리는 파일이 **경로 수준으로** 매핑되어 있는가 (스킬 / awk 카운터 / HUD / 훅 핸들러 / 회귀가드 / 벤더링 바이너리 경로)
- [ ] `scripts/ci/check-regression-guard.sh`가 전 항목 PASS이고, **새 규칙을 고정하는 회귀 케이스가 추가**되었으며, 그 케이스가 규칙을 무력화했을 때 실제로 FAIL하는 것이 확인되었는가
- [ ] 벤더링 바이너리(`bin/harness-*`)가 새 마커를 모르는 상태에서도 시스템이 오작동하지 않는가 (바이너리는 이 저장소에서 재빌드할 수 없다)

## 종료 조건

체크리스트 전 항목 Yes + 검증자의 블라인드 비교에서 **백로그 팽창 방지력 85점 이상(100점 만점)**.

미달이면 지적된 항목만 다시 만들어서 재검증해라. **최대 4라운드.**
4라운드까지 통과 못 하면 멈추고, 남은 미달 항목과 그 이유를 보고해라.

같은 지적이 3라운드 연속 반복되면 접근 방식이 틀린 것이다. 멈추고 보고해라.
